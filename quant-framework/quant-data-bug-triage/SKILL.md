# 量化数据管道 Bug 归因诊断

## 何时使用

出现以下任一症状：

- 报告/信号里某个关键字段恒为 `None` 或 `0`
- 判断逻辑"恒真"或"恒假"（如量增/量缩永远只出一侧）
- 日志报 `Expecting value: line 1 column 1`、`JSONDecodeError`、`KeyError`
- 多个标的输出完全相同的结论
- 信号全量降级为 HOLD / 空仓

## 核心原则

> **日志把原因指向数据源时，不要相信它。先用最小脚本实测。**

实践中，被归因为"数据源故障"的问题里，**大部分是自身代码的字段名或量纲错误**。
`except` 吞异常 + `logger.warning` 的组合会让自身 bug 伪装成外部故障。

## 四步诊断法

### 第 0 步：先确认脚本真的跑完了（静默崩溃）

脚本 `rc=1` 但你看到的最后一行输出「看起来正常」时，别急着归因数据源 —— **崩溃点就在那一行之后**。
典型形态：把「解释器环境差异」误判成「数据/接口故障」。

实战案例（2026-09-14）：计划任务拉起的 `daily_audit.py` 连续 754 次 `rc=1`，日志末行是
`[reconcile] status=MISMATCH ...` 看似对账结果，实际是**打印下一行的 `⚠`(U+26A0) 时抛
`UnicodeEncodeError` 当场退出**，导致后续「写对账记录 / 写收盘快照」全部没执行。

排查顺序：
1. **看 stderr，不要只看 stdout 末行**。异常只落在 stderr；日志只记 stdout 末行 = 原因完全不可见。
   → 若监控脚本只记 stdout，先补上 stderr 末行（这是一行改动，收益极高）。
2. **对比「手动跑」与「被调度跑」的环境差异**：
   ```bash
   python -c "import os; print({k: os.environ.get(k) for k in
       ['PYTHONUTF8','PYTHONIOENCODING','LANG','LC_ALL']})"
   ```
   `PYTHONUTF8=1` 常见于交互 shell，**计划任务/cron 里没有** ⇒ 手动成功、调度必败。
3. **验证 stdout 实际编码**：`print(sys.stdout.encoding)`。管道/重定向下 Python 用 locale
   （中文 Windows = cp936），**cp936 无法编码 `⚠ ✓ ✗ • 🎯 📉` 等符号** → 打印即崩。
   ```bash
   python -c "print('⚠'.encode('cp936'))"   # UnicodeEncodeError -> 确认地雷
   ```
4. **修复走「脚本自保护」而非「改调用方」**：在脚本里统一强制 UTF-8（与调用方解码约定一致）：
   ```python
   for _stream in (sys.stdout, sys.stderr):
       try: _stream.reconfigure(encoding="utf-8", errors="replace")
       except Exception: pass
   ```
   若同一项目已有脚本这么做（如 daemon 的 `_force_utf8_stdio()`），**照抄其约定**，
   并给所有「被调度器以独立进程拉起」的脚本补齐 —— 只修一个等于留下同类地雷。
5. **排查同类路径**：扫一遍同链路脚本里是否存在非 GBK 字符：
   ```python
   bad = {c for c in open(f, encoding='utf-8').read() if _not_gbk(c)}   # c.encode('cp936') 抛异常
   ```
   注意区分：**被 import 的模块**会继承主进程已重设的 stdout（安全），
   **被 Popen 独立拉起的脚本**不会（有风险）—— 风险集 = 调度器直接 spawn 的那几个。

### 第 1 步：最小脚本实测数据源

脱离业务代码，用最简请求直接打接口，打印原始响应：

```python
import requests
r = requests.get(URL, params=P, timeout=10, proxies={}, headers=H)
print(r.status_code, len(r.text))
print(repr(r.text[:200]))          # 看原始文本，不要只看 .json()
try:
    d = r.json(); print('JSON OK, rows =', len(d))
    if isinstance(d, list) and d: print('keys =', list(d[0].keys()))
except Exception as e:
    print('JSON FAIL:', type(e).__name__, e)
```

**判定**：
- 200 + 合法 JSON → **数据源正常，问题在自己的代码**，进入第 2 步
- 非 200 / 非 JSON → 才是真数据源问题，进入第 4 步

### 第 2 步：核对字段名（最高频根因）

拿第 1 步打印的真实 `keys()`，逐字比对代码里的取值语句：

```python
# 常见错误：字段名凭记忆写
row.get("name")       # 实际没有这个键 → None
row.get("current")    # 实际没有这个键 → None

# 正确做法：用实测到的真实字段名
row.get("index_name")
row.get("current_price")
```

**排查要点**：`dict.get()` 缺失键返回 `None` 而不报错，是最隐蔽的失败方式。
对所有 `get()` 取值，都要确认键名在真实响应里存在。

### 第 3 步：核对量纲与单位

同一业务指标从不同数据源取来时，单位常常不同：

| 易混概念 | 常见单位 | 量级差异 |
|---|---|---|
| 成交量 vs 成交额 | 股 vs 元 | 约 10 倍（取决于股价） |
| 金额 元 vs 万元 vs 亿元 | — | 1e4 / 1e8 |
| 百分比 vs 小数 | % vs 0~1 | 100 倍 |

**验证方法**：算比值并检查是否落在合理区间。

```python
ratio = current_vol / ma5_vol
assert 0.2 < ratio < 5.0, f"比值 {ratio:.2f} 超出合理区间，疑似量纲错配"
```

**典型症状**：错配后比值恒 >10（或恒 <0.1），判断逻辑退化为单向输出（恒判"量增"）。

### 第 3.5 步：核对缺失值哨兵与字段类型

外部接口对缺失值极少返回 `null`，常返回**字符串哨兵**。按危险度排序：

| 哨兵形式 | 危险度 | 说明 |
|---|---|---|
| `"-"` | 💥 最高 | 参与算术**立即抛 TypeError**，但若被 except 吞掉就变成静默降级 |
| `""` 空串 | 💥 高 | 同上 |
| `0` | ⚠️ 中 | 不崩，但会把「缺失」静默当成「真实为 0」，污染统计 |
| `-1` / `999999` | ⚠️ 中 | 不崩，但会算出看似合理的错误结果 |
| 数字字符串 `"12.5"` | ⚠️ 低 | 比较运算会失败（`"12.5" > 10` 抛异常；`"9" > "10"` 判 True） |

**关键陷阱**：`dict.get(key, 0)` 的默认值**只兜住「键不存在」**，
对「键存在但值是 `"-"`」完全无效。下面这行看着很安全，实际必崩：

```python
round(s.get("f204", 0) / 1e4, 2)   # f204 = "-" → TypeError
```

**自查方法**：在第 1 步的探针里打印每个字段的**运行时类型**，而非只打印值：

```python
for k, v in row.items():
    print(f"  {k}: {v!r}  type={type(v).__name__}")
```

**统一数值化的正确做法**——保留「缺失」与「为 0」的语义差异，不要把缺失静默当 0：

```python
def _to_float(value, scale=1.0, ndigits=2):
    """非数值一律返回 None，而非 0。"""
    if value is None or isinstance(value, bool):
        return None            # bool 是 int 子类，混入财务字段属数据错误
    try:
        return round(float(value) / scale, ndigits)
    except (TypeError, ValueError):
        return None
```

### 第 3.6 步：警惕「字段语义整体错位」

比单个字段名写错更隐蔽：**两个字段的用途被整体对调**，且恰好其中一个会崩。

真实案例（东财 `push2/clist`）：

| 字段 | 代码原用途 | **实际语义** | 后果 |
|---|---|---|---|
| `f204` | `main_net_inflow` | 恒为 `"-"` | 💥 崩溃，掩盖了下面的错位 |
| `f62` | `turnover_rate` | **主力净流入额（元）** | 🔴 换手率被填成资金数据 |
| `f8` | 未读取 | **真实换手率（%）** | 从未被使用 |

即「主力净流入」与「换手率」取值整体错位。**崩溃的那个字段反而是幸运的**——
它暴露了问题；如果 `f204` 恰好返回 0，错位会静默存活很久。

**自查方法**：修复类型错误时，**顺手核对同一结构里每个字段的语义**，
按数值量级做常识校验（主力净流入 12 亿合理，换手率 12 亿显然荒谬）：

```python
# 量级常识校验：换手率不可能 >1000
assert 0 <= row["turnover_rate"] <= 1000, f"换手率 {row['turnover_rate']} 量级异常"
```

### 第 3.7 步：排查同类崩溃路径

修完一处 `x / const` 崩溃后，**全文件搜索相同模式**，因为它们往往同源：

```
# 搜索所有除法点，逐个确认被除数是否可能为哨兵字符串
grep -n 'get("f[0-9]*", 0) /\|/ 1e[48]\|/ 100' services/*.py
```

真实案例中，同文件的 `item.get("f6", 0) / 1e8` 有一模一样的崩溃路径，
如果只修报错的那一处，下一个数据缺失日会再崩一次。

### 第 3.8 步：量额环比背离时，先验字段健康度，再谈行情真假

同一接口的「量」与「额」在高价股主导时会正常分化，但**两者环比方向相反**（量增额减 / 量减额增）
且幅度悬殊时，第一反应容易误判成"数据源坏了"。此时不要靠历史对比下结论，用**派生比值**判：

> 个股接口通常同时返回成交量 `v` 与成交额 `a`。**`a / v` 必须约等于该股现价 `p`**。
> 这个恒等式与行情无关，只与字段是否被截断/错位/置零有关。

```python
rows = [parse(line) for line in resp]          # 含 code, v=f[6], a=f[37], p=price
for r in rows:
    ratio = r["a"] / r["v"] if r["v"] else 0
    r["ok"] = 0.95 <= ratio / r["p"] <= 1.05   # ±5% 容差
bad = [r for r in rows if not r["ok"]]
print(f"字段自洽 {len(rows)-len(bad)}/{len(rows)}", bad)
```

**判读规则**：

| 结果 | 结论 | 处置 |
|---|---|---|
| 全部自洽（≈100%） | 字段健康，**背离是真实成交结构**（如低价股放量拉低加权均价） | 照常写入，记录原因 |
| 部分不自洽 | 那些标的的某个字段异常 | 按第 2/3 步查字段名与量纲 |
| 全部不自洽且比值系统性偏移 | 量纲错配（如额的单位是万元而非元） | 按第 3 步修量纲 |

**要点**：
1. **抽样要选高成交额、高价位的龙头**（它们的量额最大，一旦异常对合计影响最大）。
2. **与跨源互校配合使用**——两者解决不同的盲区：
   - 跨源互校（如 westock vs 腾讯 gtimg）能抓「单一数据源整体故障」；
   - 字段自洽校验能抓「同源内部字段错位/截断」，且**不依赖任何第二数据源**。
3. 实战案例（2026-09-23）：港股 gtimg 汇总口径「量 +1.7%、额 −39.6%」，隐含均价 17.54→10.45 港元/股，
   看似严重异常。对 10 只龙头逐个验 `f[37]/f[6]`：**10/10 落在 0.99~1.01**（腾讯 444.15/441.20、
   阿里 111.22/111.30）→ 判定为真实成交结构变化，未阻断写入。
   若当初仅凭"历史对比"处理，会误删一个正确值。

### 第 3.9 步：数值与上一交易日**逐分一致** ⇒ 是陈旧数据，不是行情巧合

接口调用 `rc=0`、字段齐全、量纲正确、时点校验也通过 —— 数据却整个属于**上一个交易日**。
多发于**非交易日**（周末/节假日）或数据源当日尚未更新时。

**为什么时点校验拦不住**：分时/快照类接口常见只返回 `code | time | price | volume | amount`，
`time` 是 `HHMM`（**当日之内**的时点），**整个载荷没有日期字段**。此时数据源会把
「最近一个交易日的完整序列」当作「最近一天」返回，末柱可能是 1500（全天完成）或当前时刻，
按 `time==HHMM` 取柱依然"取到了正确的时点值"—— 只不过那天的日期是错的。

**判据（按性价比排序）**：

| 判据 | 做法 | 说明 |
|---|---|---|
| 💥 **与上一交易日逐分一致** | 今日值与昨日记录**完全相同**（到分位/到元） | 最快的警报。真实行情不可能重合到小数点后 2~4 位 |
| ✅ 快照接口的日期字段 | `quote --raw` 的 `time`（如 `2026-09-24`） | westock/自选股类接口普遍带此字段，**必须读它** |
| ✅ 日K最新日期 | `kline <code> --period day --limit 1` | 今日已开盘则应有今日这根（盘中为临时值） |
| ✅ 独立源时间戳 | 腾讯 `qt.gtimg.cn/q=<code>` 第 31 个字段（如 `20260924161401`） | 跨源互校，排除单源故障 |
| ⚠️ 分时序列末柱 | 末柱 == 1500 但当前时间 < 15:00 | 只能当旁证：15:00 后的正常跑批也会末柱 1500 |

**修复 = 加判日守卫，而不是靠"看数值像不像"**：

```python
def data_date(code):
    """返回数据所属交易日 YYYY-MM-DD；分时表无日期列，非交易日会静默返回上一交易日序列。"""
    obj = json.loads(fetch_raw(f"quote {code} --raw"))
    obj = obj[0] if isinstance(obj, list) else obj
    return str(obj.get("time", ""))[:10]

# 写入前：仅在"目标是今天"时校验数据日期
if label == today_label():
    got, want = data_date("sh000001"), datetime.now(BJT).date().isoformat()
    if got != want:
        print(f"✗ 行情数据日期 {got} != 今日 {want} —— 休市或数据未更新，拒绝写入")
        return 3                       # 独立退出码，便于监控区分"故障"与"休市"
```

要点：
1. **守卫放在取业务数据之前**，命中即 `return`，不取值、不建行、不写入。
2. **只用独立退出码（如 `3`）** 表达"非交易日"，别混用 1/2；告警才能区分休假与故障。
3. **只对"今天"生效**（`label == today_label()`），显式指定历史日期的补写不受限。
4. **同一取数链路上的每个时段脚本都要加**——只修 09:45 那个，10:30/收盘脚本下次休假照样误写。
5. 已被误写的行要**回滚**（清空单元格并回读确认），别只改结果文件。

**实战案例（2026-09-25 中秋节）**：09:45 定格写脚本取到上证 1747.67 亿 / 深证 1950.34 亿，
与 9.24 记录**逐分完全一致** → 复查：`quote --raw` 的 `time=2026-09-24`、日K最新 2026-09-24、
gtimg 快照 `20260924161401` 三源一致 ⇒ 今日休市，数据整体是昨日序列。
已回滚误写的 `9.25` 行，并给 09:45 / 午盘 / 收盘三个脚本统一补上判日守卫。

### 第 4 步：确属数据源问题时的处理

1. **加重试**：间歇性失败（并发限流）用 2~3 次重试可解决
2. **兜底可用性标记**：降级时在输出中记录来源，例如 `vol_source: "unavailable"`，
   让问题可见而非静默为 0
3. **保留原始响应**：失败时记录 `resp.text[:200]`，便于后续定位

## 关键防御措施

### 输出里带上数据来源标记

```python
if current_vol <= 0:
    current_vol = quote.get("amount", 0) / 1e8
    vol_source = "fallback_amount" if current_vol > 0 else "unavailable"
else:
    vol_source = "primary"
```

这比"静默返回 0"强得多——问题会在输出里暴露，而不是变成看似正常的错误结论。

### 为字段名和量纲写回归测试

修好之后必须加测试锁定，防止重蹈覆辙：

```python
def test_uses_real_field_names():
    """回归保护：字段名必须与真实响应一致。"""
    real_shape = {"index_analysis": [{"index_name": "沪深300", "current_price": 4498.58}]}
    s = build(real_shape)
    assert s["ref_price"] == pytest.approx(4498.58)

def test_volume_source_is_consistent():
    """量能比较必须同源同量纲。"""
    for w in get_warnings():
        assert w["vol_source"] == "primary"
```

测试数据要**粘贴真实响应**，不要手写猜测的字段名——否则测试会跟着错误一起通过。

## 高频接口的实测参数（可直接抄）

### 东方财富 `push2/clist` —— 全市场批量取数

| 项 | 实测值 |
|---|---|
| `pz` 单页上限 | **100 行**（服务端硬限，传 500/1000/2000/6000 一律只返 100） |
| 全市场总量 | 约 5,558 只 ⇒ 必须 56 次分页 |
| 缺失值哨兵 | 字符串 `"-"` |
| 推荐并发 | 4 路 |
| 是否需要代理 | **不需要，且必须直连** |

**56 页全市场拉取实测对比**：

| 组合 | 覆盖 | 耗时 | 判定 |
|---|---|---|---|
| 代理 + 无重试 + 并发4 | 0 / 5558 | 1.75s | ❌ 代理被打爆，失败率 100% |
| **直连 + 重试3 + 并发4** | **5558 / 5558** | **2.07s** | ✅ **推荐** |
| 直连 + 无重试 + 并发4 | 5258 / 5558 | 2.54s | ⚠️ 漏约 5% |
| 直连 + 重试3 + 并发1 | 4800 / 5558 | 31.15s | ⚠️ 覆盖仅 86% |

**三条硬性要点**：① 直连（走 Clash 代理会 `ProxyError: RemoteDisconnected`）；
② 带重试（`Retry(total=3, backoff_factor=0.3)`）；③ 并发 4 路。

```python
session = requests.Session()
retry = Retry(total=3, backoff_factor=0.3, allowed_methods=["GET"])
session.mount("http://", HTTPAdapter(max_retries=retry))
session.proxies = {}                  # 关键：直连
session.headers.update(_HEADERS)

def fetch_page(pn):
    r = session.get(URL, params={"pn": pn, "pz": 100, "po": 1, "np": 1,
                                 "fltt": 2, "invt": 2, "fid": "f3",
                                 "fs": ALL_A, "fields": FIELDS}, timeout=20)
    return (r.json().get("data") or {}).get("diff") or []

with ThreadPoolExecutor(max_workers=4) as ex:
    pages = list(ex.map(fetch_page, range(1, 57)))
rows = [s for page in pages for s in page]
```

## 反面模式清单

| 反面模式 | 后果 |
|---|---|
| 用 `dict.get()` 却不验证键名存在 | 静默返回 None，一路传到底 |
| `get(key, 0)` 当成缺失值防御 | **对 `"-"` 无效，照崩** |
| 把缺失值静默转成 0 | 「缺失」与「真为 0」混为一谈，污染统计 |
| 用 `except Exception` 吞掉后返回默认值 | 自身 bug 伪装成数据源故障 |
| 只修报错的那一处除法 | 同文件的同源崩溃路径下次再犯 |
| 手写测试数据的字段名（而非粘贴真实响应） | 测试通过但线上失败 |
| 跨数据源比较同名字段（volume/amount） | 量纲错配，逻辑退化 |
| 批量取数走高并发代理 | 本机代理被打爆，失败率 100% |
| 看到"多个标的结果相同"就断定 bug | 可能是真实行情（需查数值确认） |
| 只校验 `time==HHMM` 就认为取数正确 | 分时表无日期列，**休市日会拿昨日序列当年今日**（见第 3.9 步） |
| 把"数值与昨日一模一样"当巧合放过 | 到分位重合 ⇒ 陈旧数据，立即查数据日期 |
| 发现误写只改结果 JSON、不回滚文档 | 表格里留下伪记录，后续审计/环比全部被污染 |

## 最后一条

**异常日志会撒谎。** `logger.warning("获取XXX失败")` 只说明 except 被触发，
不说明根因在外网。先实测，再归因。
